Ты эксперт по извлечению правил из документов, нормативно правовых актов, приказов и тд.
Ты извлекаешь эти правила для дальнейшей проверки по ним текстов технических заданий на разработку информационных систем.

Задача: Необходимо извлечь атомарные, проверяемые правила которые могут предьявляться к техническому заданию.

ДОКУМЕНТ:
```
{document_text}
```

ДОСТУПНЫЕ ТЕГИ:
```json
{tags_json}
```

Ты можешь использовать теги из списка выше ИЛИ придумать новый тег (короткий snake_case), если ни один не подходит.
Если ты придумываешь новый тег, ты ОБЯЗАН добавить поле "new_tag_definition" в правило.

ТРЕБОВАНИЯ К ИЗВЛЕЧЕНИЮ ПРАВИЛ:

1. Извлекай ТОЛЬКО конкретные, проверяемые требования
2. Каждое правило должно быть верифицируемым (можно проверить в ТЗ автоматически)
3. Игнорируй общие декларации ("документ должен быть качественным")
4. Фокусируйся на структурных требованиях (наличие разделов, информации)

ФОРМАТ ВЫВОДА:

Для каждого требования создай правило в формате:

{{
  "rule_id": "AUTO",
  "tag": "security",  // Существующий или придуманный тобой новый тег
  "new_tag_definition": {{  // ДОБАВЛЯЙ ТОЛЬКО ЕСЛИ ТЕГ НОВЫЙ
    "category": "functional|technical|data|security|compliance",
    "description": "Краткое описание того, что означает этот новый тег"
  }},
  "title": "Краткое название требования (до 50 символов)",

  "requirement": "ЧЁТКАЯ формулировка: что должно быть в ТЗ. Если есть варианты (OR) или минимум (2 из 3) - укажи явно. Формулировка должна быть однозначной и проверяемой.",

  "verification_method": "Пошаговая инструкция КАК проверить это требование в ТЗ. Укажи: (1) где искать (названия разделов), (2) что считается выполнением требования, (3) что НЕ считается выполнением. Инструкция должна быть настолько чёткой, чтобы два разных проверяющих пришли к одному выводу.",

  "positive_examples": [
    "Конкретные примеры формулировок/технологий, которые УДОВЛЕТВОРЯЮТ требованию",
    "Каждый пример - это реальная фраза, которая может встретиться в ТЗ",
    "Минимум 3-5 примеров"
  ],

  "negative_examples": [
    "Примеры формулировок, которые НЕ удовлетворяют требованию",
    "Обычно это слишком общие/неконкретные фразы",
    "Минимум 2-3 примера"
  ],

  "severity": "critical",  // critical | high | medium | low

  "source": {{
    "document": "Точное название документа",
    "section": "Номер и название раздела",
    "quote": "Точная цитата из документа, на основе которой создано правило (до 200 символов)"
  }}
}}

УРОВНИ КРИТИЧНОСТИ (severity):
- critical: отсутствие делает ТЗ недопустимым (безопасность, назначение системы)
- high: важное требование, сильно влияет на качество ТЗ
- medium: желательное требование, улучшает качество
- low: рекомендация, незначительное улучшение

ВАЖНЫЕ ПРАВИЛА:

1. **Одно правило = одно требование**
   - Не объединяй несколько требований в одно правило
   - Если в разделе стандарта 3 пункта → создай 3 правила

2. **Конкретность**
   - В requirement укажи ТОЧНУЮ логику: "минимум N из M", "все пункты", "хотя бы один"
   - В verification_method дай ПОШАГОВУЮ инструкцию
   - В examples используй РЕАЛЬНЫЕ формулировки

3. **Проверяемость**
   - Правило должно проверяться автоматически LLM
   - Избегай субъективных критериев ("качественный", "достаточный")
   - Фокус на наличии/отсутствии конкретной информации

4. **Примеры**
   - positive_examples: минимум 3-5 примеров
   - negative_examples: минимум 2-3 примера
   - Примеры должны быть КОНКРЕТНЫМИ (не "меры безопасности", а "OAuth 2.0")

5. **Источник**
   - quote должна быть ТОЧНОЙ цитатой, не пересказом
   - Если цитата длинная, укажи ключевую часть (до 200 символов)

6. **Теги**
   - Используй теги из предоставленного списка или создавай новые
   - Если создаешь новый тег, обязательно добавь "new_tag_definition"
   - Один тег на правило
