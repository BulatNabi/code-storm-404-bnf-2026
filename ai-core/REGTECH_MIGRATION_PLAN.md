# План перехода `ai-core` под регуляторного ассистента

## 1. Цель

Создать на базе текущего `ai-core` умного ассистента для продуктовых и инженерных команд финтеха, который по описанию новой фичи мгновенно выдаёт:

- регуляторные области, которые затронуты;
- что именно нужно проверить;
- какие документы и процессы требуется обновить.

Цель — сократить поздние переделки, снизить юридические и операционные риски, ускорить релиз.

---

## 2. Текущее состояние `ai-core`

### Структура

- `run_parser.py` — запуск процесса парсинга документа
- `chunker/` — разбор Markdown-документа, поиск заголовков, построение иерархии и чанков
- `classifier/` — классификация чанков по тегам через LLM
- `rules_generator/` — генерация правил на основе документа
- `validation/` — проверка текстов по правилам и генерация отчётов
- `common/client/llm_client.py` — обёртка над OpenAI/Yandex Qwen
- `schema/tags.json` — набор тегов для классификации

### Что уже подходит

- архитектура LLM pipeline уже готова;
- есть разделение на парсинг, классификацию, генерацию и валидацию;
- имеется общий LLM-клиент и prompt-слой.

### Что требует изменения

- текущая логика ориентирована на обработку Markdown-документов;
- теги в `schema/tags.json` общего назначения, не регуляторные;
- нет специального конвейера для анализа описания фич;
- нет бизнес-ориентированного вывода типа "проверить/обновить".

---

## 3. Архитектура нового регтех-ассистента

### Новый pipeline

1. `FeatureAnalyzer` — принимает описание фичи.
2. `RiskClassifier` — определяет регуляторные домены и риски.
3. `ChecklistGenerator` — формирует что проверить и какие документы/процессы обновить.
4. `ComplianceReporter` — формирует итоговый JSON/MD отчет.

### Основные модули

- `feature_analyzer/` или адаптация `chunker/`
- `regulatory_classifier/` или расширение `classifier/`
- `checklist_generator/` или расширение `rules_generator/`
- `compliance_validation/` или расширение `validation/`
- `schema/` — обновление тегов и объектов
- `run_feature_analysis.py` — новый CLI для фичи-анализа

## 4. Шаги миграции и разработки

### Шаг 1. Адаптация зависимостей

Обновить `ai-core/requirements.txt` с реальными библиотеками:

- `openai>=1.0.0`
- `python-dotenv>=1.0.0`
- возможно: `pydantic>=2.0.0` или `typer>=0.9.0` для удобного CLI
- `rich>=13.0.0` если нужен красивый вывод в терминале

> В текущем коде `docling` не используется, поэтому его можно удалить, если он не нужен для внешних задач.

### Шаг 2. Обновить схему тегов `schema/tags.json`

Добавить новые регуляторные теги, например:

- `data_privacy`
- `aml` / `anti_money_laundering`
- `kyc`
- `payment_regulation`
- `consumer_protection`
- `cross_border_payments`
- `license_requirements`
- `risk_management`
- `reporting_requirements`
- `information_security`
- `consumer_disclosure`
- `contractual_terms`
- `transaction_monitoring`

Каждый тег должен содержать понятное описание, чтобы LLM мог использовать его как target.

### Шаг 3. Переназначить `classifier` под описание фичи

Вместо классификации MD-чанков сделать классификацию текстового описания фичи.

Варианты:

- переименовать `classifier/processor.py` в `feature_classifier.py` и адаптировать prompt;
- сохранить `ChunkClassifier`, но добавить новый интерфейс `FeatureClassifier`.

Новый муспрост:

- вход: текст описания фичи
- выход:
  - упомянутые регуляторные области
  - список релевантных тегов
  - уровень риска или приоритет

Пример JSON-результата:

```json
{
  "feature_id": "new_payment_flow",
  "feature_title": "Автоматический перевод на новый кошелёк",
  "regulatory_domains": ["payment_regulation", "aml", "consumer_protection"],
  "risk_summary": "Высокий риск из-за KYC и проверки переводов, требуется обновить процедуру анти-отмывания и пользовательское соглашение.",
  "tags": ["payment_regulation", "kyc", "aml"]
}
```

### Шаг 4. Добавить генератор проверки и документов

В существующем `rules_generator/` можно создать новый `feature_checklist.py`.

Он должен генерировать:

- что проверить в рамках регуляторной области;
- какие бизнес-процессы требуют изменения;
- какие документы нужно обновить (регламенты, политики, инструкции, договора);
- порядок действий или рекомендации по вовлечению compliance/юркоманды.

Пример вывода:

```json
{
  "feature_id": "new_payment_flow",
  "actions": [
    "Проверить, соответствует ли схема перевода требованиям закона о платежных услугах",
    "Обновить KYC-процедуру для новых типов получателей",
    "Проверить сроки хранения данных согласно PII/PDPL",
    "Обновить внутренний процесс мониторинга подозрительных операций"
  ],
  "documents_to_update": [
    "Политика по работе с персональными данными",
    "Процедура KYC/EDD",
    "Материалы для клиента: правила и пользовательское соглашение"
  ]
}
```

### Шаг 5. Встроить экспертные prompt’ы по регуляторике

Создать набор prompt-файлов в `ai-core/prompts/` или `chunker/prompts/`:

- `feature_regulatory_classification.txt`
- `feature_checklist_generation.txt`
- `feature_documentation_recommendations.txt`

Примеры инструкций для prompt-а:

- "Ты эксперт по регуляторике финтеха Узбекистана и международных платежных стандартов."
- "Определи ключевые риски, области проверки и необходимые документы по описанию фичи."
- "Выведи только JSON с тремя секциями: regulatory_domains, checks, docs_to_update."

### Шаг 6. Создать новый CLI/сервис

Новый файл `run_feature_analysis.py`:

- принимает `--input` текстовое описание или файл
- опционально `--output-json`, `--output-md`
- запускает цикл: классификация -> чеклист -> отчет

Пример команды:

```bash
python run_feature_analysis.py --input features/new_payment_flow.txt --output-json reports/feature_risk.json
```

### Шаг 7. Адаптировать `validation`

`validation/` можно использовать как модуль для финальной проверки рекомендаций:

- проверить, что ответ LLM соответствует набору внутренних правил;
- сформировать отчет о потенциальных пробелах;
- выдать уровень уверенности и предложения по следующему шагу.

### Шаг 8. Обновить документацию

Добавить файл с описанием архитектуры, prompt-стратегии и форматов выходных данных.

- этот файл может быть `ai-core/REGTECH_MIGRATION_PLAN.md`
- отдельный документ — `docs/regtech_assistant_design.md`

## 5. Конкретные изменения по папкам

### `ai-core/schema/tags.json`

- расширить набор тегов регуляторной направленности;
- сохранить существующие теги, если они могут пригодиться для более широкого анализа.

### `ai-core/common/client/llm_client.py`

- оставить как есть;
- при необходимости добавить поддержку нового response_format для JSON-схем.

### `ai-core/classifier/`

- добавить `FeatureClassifier`;
- расширить `prompt.py` для feature-level классификации;
- возможно выделить новый модуль `feature_models.py`.

### `ai-core/rules_generator/`

- добавить `feature_checklist.py`;
- использовать существующую `RuleGenerator` логику как шаблон для генерации текста/JSON.

### `ai-core/validation/`

- добавить новый use case `feature_validation.py`;
- использовать `Validator` как основу для проверки соответствия рекомендаций.

### `ai-core/run_parser.py`

- переименовать в `run_feature_analysis.py` или добавить новый скрипт рядом.
- старый `run_parser.py` можно оставить для работы с документами, если он ещё нужен.

## 7. Формат выходных данных

Рекомендуемый JSON-формат ответа ассистента:

```json
{
  "feature_id": "<id>",
  "title": "<название фичи>",
  "summary": "Краткий вывод о рисках и рекомендуемых действиях",
  "regulatory_domains": ["..."],
  "risk_level": "low|medium|high",
  "checks": [
    "..."
  ],
  "documents_to_update": [
    "..."
  ],
  "processes_to_update": [
    "..."
  ],
  "explainers": [
    {
      "domain": "...",
      "reason": "..."
    }
  ]
}
```

Дополнительно можно генерировать Markdown-отчёт с разделами:

- Описание фичи
- Затронутые регуляторные области
- Рекомендации
- Документы и процессы
- Следующие шаги

---

## 8. Риски и внимание

- Текущий `ai-core` основан на LLM; важно строго задавать prompt и проверять корректность JSON-ответов.
- Регуляторный фич-риск должен проверяться юристом/комплаенсом, LLM здесь — помощник, а не окончательное решение.
- Нужна нормализация терминов регуляторных доменов и контроль за тем, что классификатор не плодит ненужные теги.

2. создать новый prompt-компонент;
3. реализовать `run_feature_analysis.py` с простым экспериментальным output;
4. прогнать описание одной фичи и проверить результат.
