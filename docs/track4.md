# Дорожка 4. Финтех-регуляторный радар

## Проблема

Продуктовые и инженерные команды часто поздно узнают, что новая фича затрагивает AML, KYC, PSD2/PSD3, персональные данные, AI Act или требования к платежам.

## Что нужно сделать

Сделать ассистента, который по описанию фичи определяет потенциальные регуляторные риски и формирует план действия для команды.

## Ограничения

- Решение должно обрабатывать запрос и выдавать результат в реальном времени.
- Разрешено использование любых доступных LLM (через API или развернутых локально).
- Интерфейс должен быть минималистичным и понятным нетехническим специалистам.

## Что должно быть в демо (MVP)

- **Ввод:** Текстовое поле, куда копируется описание продуктовой фичи (в формате user story или свободного текста).
- **Детекция зон:** Чёткий вывод затронутых регуляторных областей (KYC, AML, fraud, data privacy, credit scoring, open banking, crypto и др.).
- **Чеклист:** Сгенерированный пошаговый список проверок для Product Owner и специалиста по Compliance.
- **Рекомендации:** Перечень документов, политик или пользовательских соглашений, которые потребуется обновить в связи с релизом.

## Опционально (усложнение)

- **Бесшовная интеграция:** Настройка связи с рабочими таск-трекерами.
- **Пруфы:** Ассистент не просто называет область риска, но и даёт короткую ссылку на конкретный закон или директиву.

## Критерии оценки

| Критерий | Описание |
|---|---|
| **Точность алгоритма** | Способность системы «понимать» неочевидные риски из контекста (например, распознать риск для data privacy в задаче «добавить кнопку шаринга контактов») |
| **Применимость на практике** | Насколько сгенерированные чеклисты и рекомендации адекватны и полезны для реальной работы PO |
| **Качество интеграции** | Работает ли связка с трекером задач без ручного копирования информации (для усложнения) |
| **UX/UI продукта** | Удобство использования инструмента для конечного пользователя |
